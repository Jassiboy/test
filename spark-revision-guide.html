Wide Transformation: groupBy and shuffle

A wide transformation is one where one output partition depends on data from several input partitions. In this example, identical keys begin in P0–P3 on two executors, so Spark must redistribute them before it can produce one final count per key.

Code being executed

from pyspark.sql import functions as F

# The file scan in this teaching example produces four input partitions: P0–P3.
df = spark.read.parquet("/data/events")

result = (
    df.groupBy("key")
      .agg(F.count("*").alias("row_count"))
)

result.show()

The twelve illustrative input rows are distributed as follows:

P0 on Executor A: A, A, B
P1 on Executor A: B, C, A
P2 on Executor B: A, C, C
P3 on Executor B: B, B, C

Expected result: A → 4, B → 4, C → 4

Physical plan shape

HashAggregate(keys=[key], functions=[count(1)])          ← final aggregation
+- Exchange hashpartitioning(key, 3)                     ← wide boundary / shuffle
   +- HashAggregate(keys=[key], functions=[partial_count(1)])
      +- FileScan parquet [key]                          ← input scan

Stage-by-stage verbal walkthrough

Stage 0 · Scan, partial aggregate and shuffle write

1
Scan the input filesSpark converts file splits into DataFrame partitions P0–P3. One task processes each partition. In this example, Executor A runs P0/P1 and Executor B runs P2/P3.
2
Build a partial count inside each taskEach task creates a task-local aggregation map. P0 produces A:2 and B:1; P1 produces A:1, B:1 and C:1; P2 produces A:1 and C:2; P3 produces B:2 and C:1.
3
Choose a global shuffle bucket for every keyThe partitioning expression deterministically maps all A values to B0, all B values to B1 and all C values to B2 in this illustration. The bucket is logical and cluster-wide; it is not permanently owned by an executor.
4
Write map-output segments to executor-local diskEvery map task writes its B0/B1/B2 byte ranges into a consolidated shuffle data file plus an index file. These files stay on the worker where that map task ran until downstream reduce-side tasks—also called reducer tasks—fetch them.

Stage 1 · Shuffle read and final aggregation

5
Schedule one reducer task per shuffle partitionThese are the downstream shuffle-read or reduce-side tasks. R0 is responsible for B0, R1 for B1 and R2 for B2. The TaskScheduler places them on executors with available slots; the mapping is dynamic rather than permanently round robin.
6
Fetch local and remote shuffle blocksEach reducer task reads only its assigned bucket segment from every map output. Segments on the same worker use a local read; segments on another worker cross the network.
7
Merge and finish the countR0 combines all partial A counts into A:4, R1 produces B:4 and R2 produces C:4. A task may use memory and spill temporary state to local disk if required.
8
Return or write the final resultThe show() action collects the small displayed result to the driver. A file-writing action would instead have the downstream reducer tasks write their output partitions to destination storage.
Terminology: on this page, reducer task, reduce-side task and downstream shuffle-read task refer to the same conceptual role: a Spark task that consumes one shuffle partition. It is not a separate permanent Hadoop Reducer process; it is an ordinary Spark task scheduled on an available executor.

What the consolidated shuffle data and index files contain

Under Spark’s normal sort-based shuffle, one completed map task usually produces one consolidated data file and one index file for that shuffle. It does not normally produce a separate physical file for B0, B1 and B2.

FileWhat it physically containsHow it is used
shuffle_7_0_0.dataThe serialized—and normally compressed—map-output records or partial aggregates, arranged as consecutive byte ranges: first B0, then B1, then B2.A downstream reducer task reads only the byte range belonging to its assigned shuffle partition.
shuffle_7_0_0.indexnumberOfShufflePartitions + 1 byte offsets marking where every bucket range starts and ends in the data file.Spark looks up two adjacent offsets to locate a bucket without scanning the entire data file.

For map task M0, whose partial output is A:2 for B0, B:1 for B1 and nothing for B2, the files can be pictured like this:

M0 consolidated data file
┌────────────────────────────┬────────────────────────┬──────────┐
│ B0 bytes: serialized (A,2) │ B1 bytes: serialized   │ B2 empty │
│ byte range [0,48)          │ (B,1), range [48,92)   │ [92,92)  │
└────────────────────────────┴────────────────────────┴──────────┘

M0 index file
offsets = [0, 48, 92, 92]
           │   │   │   └─ end of B2
           │   │   └───── start of B2 / end of B1
           │   └───────── start of B1 / end of B0
           └───────────── start of B0

If R1 is responsible for B1, it asks for M0’s B1 block. Spark reads offsets 48 and 92 from the index and fetches only [48,92) from the data file. If R1 runs on the same worker as M0, that is a local read; otherwise those bytes are served across the network.

Important: “segment” or “shuffle block” normally means a byte range inside the consolidated data file. The index entry identifies the range; it is not the shuffled data itself. Empty buckets have equal start and end offsets and therefore occupy zero data bytes.

Global shuffle buckets, local map segments

The three shuffle buckets are global logical destinations for the entire shuffle. They are not three central containers, and they are not divided as some buckets belonging permanently to Executor A and the rest to Executor B.

Executor A local disk

Executor A ran map tasks M0 and M1, so its disk stores the map-output files created by M0 and M1.

M0: B0[A:2] B1[B:1] B2[empty]
M1: B0[A:1] B1[B:1] B2[C:1]

Executor B local disk

Executor B ran map tasks M2 and M3, so its disk stores the map-output files created by M2 and M3.

M2: B0[A:1] B1[empty] B2[C:2]
M3: B0[empty] B1[B:2] B2[C:1]

Stage 1 reducers

Each reducer fetches only its bucket segment from every mapper. Local blocks come from the same executor; remote blocks cross the network.

R0 fetches all B0 pieces → A:4
R1 fetches all B1 pieces → B:4
R2 fetches all B2 pieces → C:4

No segment is fetched by all three reducers. Reducer 0 fetches only B0, Reducer 1 only B1 and Reducer 2 only B2. Each map-output segment therefore belongs to exactly one logical reduce partition. The repeated-looking activity is different reducers collecting different columns of the matrix.

Physical files and local-versus-network reads

  • Map side writes one data file + one index file per map task to executor local disk, sorted by target partition ID. B0, B1 and B2 are normally byte-range segments inside that consolidated data file, not three separate bucket files.
  • Reduce side: each reduce task fetches its segment from every map output. With two evenly used executors, roughly half the bytes may be read from the reducer executor’s local disk and half may cross the network. With three evenly used executors, roughly one-third may be local and two-thirds remote.

The local fraction is only an estimate. It depends on where the reducer is scheduled and how many relevant map outputs were produced on that same executor.

1. Which executor runs that task?

Spark’s driver-side TaskScheduler assigns pending tasks to executor slots as executors offer resources. It considers:

  • Available executor cores/slots
  • Data locality preferences
  • Resource requirements
  • FIFO or FAIR scheduling between jobs/stages
  • Failed-task retries and speculative execution
  • Executor availability at that moment

Reduce tasks commonly fetch shuffle blocks from many executors, so they often have weak locality preferences and are placed on whichever suitable executor has a free slot. Spark can sometimes favor an executor holding more of that partition’s shuffle data, but this is an optimization—not a permanent mapping.

The important point is:

Shuffle partition → reduce task: deterministic
Reduce task → executor: dynamic scheduling

What happens when the shuffle partition count is one?

Q: If the shuffle partition count is reduced to one, does Spark still shuffle the data?

Yes. One shuffle partition means there is one logical destination bucket and one downstream reducer task. It does not mean that the Exchange or stage boundary disappears.

spark.conf.set("spark.sql.shuffle.partitions", 1)

df.groupBy("key").count()

Final HashAggregate
└─ Exchange hashpartitioning(key, 1)
   └─ Partial HashAggregate
      └─ FileScan

Q: How does the shuffle happen with only one bucket?

The four Stage-0 map tasks still scan and partially aggregate their own input partitions. Because the partition count is one, every partial result is written into Bucket 0:

Executor A                           Executor B
M0 → B0: A:2, B:1                  M2 → B0: A:1, C:2
M1 → B0: A:1, B:1, C:1             M3 → B0: B:2, C:1

                 all Bucket-0 segments
                          ↓
                    Reducer task R0
                          ↓
                  A:4 · B:4 · C:4

Each map task still writes its consolidated shuffle data file and index file on executor-local disk. In this case, each file has one nonempty shuffle-partition range: B0.

Q: Does the reducer read everything over the network?

Not necessarily. Suppose R0 is scheduled on Executor A:

M0 Bucket 0 on Executor A → local read
M1 Bucket 0 on Executor A → local read
M2 Bucket 0 on Executor B → remote network fetch
M3 Bucket 0 on Executor B → remote network fetch

The shuffle still exists even though some blocks are local. Shuffle describes the redistribution and dependency boundary; network traffic depends on where the reducer task is scheduled relative to the map-output files.

Q: Why is a shuffle required if all records go to one partition?

The final aggregation needs partial results from every upstream partition. Spark must materialize those map outputs and make all of them available to the single downstream task. The fact that there is one destination concentrates the redistribution; it does not remove it.

One shuffle partition ≠ no shuffle

It means:
all map outputs target one logical bucket
                    +
one reducer task fetches every bucket segment

Q: How many tasks are created?

StageTask count in this exampleWork
Stage 04 map-side tasksScan P0–P3, partially aggregate and write Bucket-0 shuffle segments.
Stage 11 reducer taskFetch every Bucket-0 segment and perform the final aggregation.

Map-side parallelism remains. Reduce-side parallelism becomes one.

Q: What is the performance consequence?

  • Only one executor core performs the final aggregation.
  • The single reducer fetches the complete shuffled result.
  • Its memory requirement and spill risk are much larger.
  • The reducer can become the job’s bottleneck or straggler.
  • The final result has one Spark partition and one downstream output task.

Q: Is this the same as coalesce(1)?

No. The operations have different dependency behavior:

spark.sql.shuffle.partitions = 1 during groupBy
→ aggregation still requires an Exchange
→ all map outputs target one shuffle partition
→ one reducer task

repartition(1)
→ explicitly creates a shuffle
→ one downstream partition

coalesce(1)
→ normally creates a narrow dependency without a new shuffle
→ one child partition claims multiple parent partitions

coalesce(1) does not remove an Exchange already required by an earlier groupBy, join or distinct operation.

Summary: reducing the shuffle partition count to one still shuffles the data. All Stage-0 tasks write to one logical bucket, and one downstream reducer task fetches and processes every segment.

Detailed written walkthrough: one executor, four cores and 16 GB heap

Scenario: read a 50 GB Parquet dataset, run groupBy(key).count(), and call show() as the action.

Step 0

Before show(): Spark is lazy

spark.read.parquet(...) and groupBy(...).count() build a logical plan on the driver. Spark may list files and inspect schema metadata, but it does not scan the 50 GB dataset or start executor tasks yet.

Step 1

show() triggers the job

Catalyst optimizes the logical plan and Spark creates a physical plan:

Scan parquet → HashAggregate(partial_count) → Exchange hashpartitioning(key, 200) → HashAggregate(final_count) → CollectLimit 20

The Exchange is the shuffle boundary. It separates the upstream scan and partial aggregation from the downstream shuffle read and final aggregation.

Step 2

Create input partitions and Stage-0 tasks

50 GB × 1024 ÷ 128 MB ≈ 400 input partitions ≈ 400 Stage-0 tasks

The executor has four cores, so only four tasks can run simultaneously. The stage therefore needs approximately 100 task waves.

Step 3

Stage 0: what each map task does

  1. Read one approximately 128 MB input split in smaller Parquet or columnar batches.
  2. Update a per-task in-memory hash map containing one partial count per key seen in that input partition.
  3. Hash each partial key with hash(key) % 200.
  4. Pass the partial records through the shuffle writer and write indexed bucket segments to executor-local disk.
  5. Release the task’s scan, aggregation and shuffle-buffer memory when the task completes.

The partial aggregate can reduce shuffle data significantly. If each partition contains many repeated rows for only 1,000 keys, the mapper writes at most roughly 1,000 partial key-count rows. If nearly every row has a different key, the partial aggregation reduces far less and the shuffle can remain large.

Step 4

Stage 1: what each downstream task does

After the shuffle-map stage completes, Spark schedules approximately 200 downstream tasks before AQE changes the partition count. Each task:

  1. Fetches one logical shuffle bucket’s segments from every mapper.
  2. With one executor, reads those segments from the same machine’s local shuffle storage rather than across executors.
  3. Deserializes and merges the partial counts in final aggregation state.
  4. Produces final key → count rows for that result partition.

Even though show() displays only 20 rows, the distributed groupBy must account for the full input before the final counts are correct.

Step 5

show() displays the result

The final counts remain distributed across executor result partitions. CollectLimit 20 obtains only the rows needed for display and sends those rows—not the original 50 GB dataset—to the driver.

Memory check: A 16 GB executor heap has roughly 9.4 GB in Spark’s unified execution-and-storage region under the common default memory fraction. Four active tasks dynamically share this pool. Dividing 9.4 GB by four gives roughly 2.35 GB as an intuitive average capacity, but Spark does not reserve a fixed 2.35 GB block for each task. A task may acquire more or less depending on competing tasks, cached blocks and execution-memory pressure.

The map stage does not become one task. Only the reduce side collapses to one task. That reducer receives all post-combine keys, so it can become slow, spill heavily, or fail from memory pressure. Use one shuffle partition only when the shuffled result is genuinely small or a single output partition is required.

Why can a reducer spill when shuffle data is already on disk?

The existing shuffle files and reducer spill files serve different purposes. Map-side shuffle files contain the serialized input blocks waiting for reducers. The reducer must still fetch those blocks, deserialize their records, and build in-memory sorting or aggregation state.

Map-side shuffle files on executor disks
                 ↓ fetch selected bucket blocks
Reducer execution memory
├── network and local-fetch buffers
├── deserialized records
├── aggregation hash map
└── sorting and merge state
                 ↓ working state exceeds available memory
Reducer-side temporary spill files on local disk
  • Map-side shuffle files: output produced by Stage 0 and consumed by Stage 1.
  • Reducer spill files: temporary working data evicted from the reducer’s execution memory.
  • Slow disk with free capacity: the task may succeed but becomes much slower.
  • Disk capacity exhausted: the task normally fails with an I/O or “No space left on device” error.
  • Non-spillable state or a huge record/key: the executor can still fail with an out-of-memory error.
Interview wording: “Shuffle files are the reducer’s input stored on map executors. Reducer spill is additional temporary output created when the reducer’s deserialized aggregation or sorting state cannot fit in execution memory.”

FAQ

Clarifying the recent Spark shuffle doubts

1. What are map and reduce? Are they tasks?

Yes. A map-style task processes one input partition. It scans data, performs transformations or partial aggregation, and may write shuffle output.

A reduce-style task processes one shuffle partition. It fetches matching map-output blocks, merges them, and produces the downstream result.

Stage 0: input partition → map task → shuffle files
Stage 1: shuffle partition → reduce-style task → final aggregation

Technically, Spark commonly uses ShuffleMapTask for the upstream stage and ResultTask for the final stage. “Reduce task” is the usual informal name for a downstream task that reads shuffle data.

2. Do map and reduce tasks occur only when there is a shuffle?

No. Map-style tasks also perform ordinary scans, filters and projections in a single-stage job that has no shuffle.

Reduce-style processing appears after an Exchange or shuffle boundary because the downstream tasks must read shuffled partitions.

No shuffle:
Scan → Filter → Projection → Result
One stage containing partition-processing tasks

With shuffle:
Scan → Partial Aggregate → Exchange → Final Aggregate
Stage 0 map tasks              Stage 1 downstream tasks

3. What happens if the shuffle partition count is set to one?

Stage 0 can still have approximately 400 parallel map tasks for the 50 GB input. However, every mapper writes to the same logical Bucket 0, and Stage 1 has only one downstream task.

≈400 map tasks → distributed Bucket-0 segments → one reducer task

Map-stage parallelism remains.
Reduce-stage parallelism becomes one.

That single reducer must fetch every Bucket-0 segment and process all post-combine keys on one core. It can become a straggler, spill heavily, or fail.

4. If the single reducer has too much data, will it always throw an OutOfMemoryError?

Disk is slow but has spaceThe task may finish, but it becomes very slow because of repeated writes and merges.
Disk capacity is exhaustedThe task normally fails with an I/O or “No space left on device” error, not an OOM.
Non-spillable memory is too largeThe executor can fail with an OutOfMemoryError.

Spilling lowers heap pressure but does not guarantee success. A huge record, one extreme key, deserialization state, fetch buffers, a UDF, or other non-spillable structures can still exhaust memory.

5. If shuffle data is already on disk, why can the reducer spill again?

The original shuffle files and reducer spill files serve different purposes.

Map-executor local disk:
Map-side shuffle blocks waiting to be fetched
                 ↓ local or network fetch
Reducer execution memory:
Fetch buffers + deserialized rows + hash map + sorting/merge state
                 ↓ insufficient memory
Reducer local disk:
Additional temporary spill runs

The reducer cannot calculate final counts inside the original map-output files. It must fetch, deserialize, merge, sort or aggregate the data. When that working state exceeds execution memory, Spark writes additional temporary spill files to the reducer executor’s local disk.

6. In the 50 GB example, how many map and reduce tasks are created?

With approximately 128 MB input partitions, Stage 0 creates roughly 400 map tasks.

With 200 configured shuffle partitions, Stage 1 creates roughly 200 downstream tasks before Adaptive Query Execution changes the partition count.

50 GB ÷ 128 MB ≈ 400 Stage-0 tasks
200 shuffle partitions = 200 Stage-1 tasks

If shuffle partitions = 1:
400 Stage-0 tasks, but only 1 Stage-1 task

Memory and shuffle-storage questions for the 50 GB scenario

7. Where does each task’s partial groupBy hash map live?

It lives inside the executor JVM and consumes Spark execution memory from the unified memory region. It is per task, so four concurrently running tasks can have four independent aggregation maps competing for the same shared pool.

Executor: 16 GB heap ├── Reserved memory: approximately 300 MB ├── Unified Spark memory: approximately 9.4 GB │ ├── Execution: aggregation maps, joins and shuffle sorting │ └── Storage: cached blocks and broadcast data └── User and internal memory: remaining heap Outside the heap: memoryOverhead covers direct/native buffers, Python workers and container overhead.

The execution and storage regions share the unified pool dynamically. Four tasks do not receive four permanently reserved equal slices.

8. Does a completed task’s hash map persist into the next task wave?

No. The hash map belongs to one task and one input partition. When that task finishes writing its shuffle output, the aggregation and shuffle-buffer memory is released. The next task starts with a fresh empty hash map.

Wave 1:
Task 0 map → shuffle file M0 → task memory released
Task 1 map → shuffle file M1 → task memory released

Wave 2:
Task 4 starts with a new empty map
Task 5 starts with a new empty map

What survives between waves is the completed map task’s shuffle output on local disk—not its in-memory hash map. Explicit cache() is a different operation and uses storage memory.

9. Does a task with many distinct keys create skew?

Many distinct keys inside a task primarily create high cardinality and memory pressure. They make the task’s aggregation map larger and can cause spill.

Skew means data is distributed unevenly across downstream shuffle partitions—for example, one reducer receives far more bytes or records than the others.

High cardinality:
many different keys → large hash map → memory pressure / spill

Skew:
uneven key distribution → one large reducer partition → straggler

A hot repeated key does not necessarily create a large map-side hash map because repeated rows combine into one entry. Its problem appears downstream when the hot key’s records or state make one reducer disproportionately expensive.

10. Where are the 200 shuffle buckets stored?

They are not 200 permanent regions inside executor memory. They are global logical reducer-partition IDs.

A task briefly buffers records and sorting metadata in execution memory. Under normal sort-based shuffle, the completed map output is written as a consolidated data file plus an index file. The index records the byte range for each bucket segment.

Map task M17 data file:
[Bucket 0 bytes][Bucket 1 bytes] ... [Bucket 199 bytes]

Map task M17 index file:
offsets identifying where each bucket segment begins and ends

With approximately 400 map tasks, Spark has roughly 400 map-output data/index pairs, rather than requiring 400 × 200 large standalone bucket files.

11. Are the 200 buckets divided evenly between multiple executors?

Not as “buckets 0–99 on Executor A and 100–199 on Executor B.” Each executor stores the map-output files created by the map tasks that ran there. Those files may contain segments for any of the 200 bucket IDs.

Logical Bucket 7:
├── M0 Bucket-7 segment — Executor A disk
├── M1 Bucket-7 segment — Executor A disk
├── M2 Bucket-7 segment — Executor B disk
└── ... one possible segment from every mapper

Reducer 7 fetches all Bucket-7 segments.
  • Physical shuffle bytes across executors depend on map-task placement and how much each mapper writes.
  • Bucket sizes depend on key distribution. Hashing many distinct keys is often reasonably balanced, but hot keys can still create skew.

12. What does executor-local disk mean, and how large is it?

Local disk is storage attached or mounted to the machine or container running the executor. It is separate from the 16 GB executor heap.

  • Standalone or general deployments: configured through spark.local.dir.
  • YARN: normally uses the NodeManager’s configured local directories.
  • Kubernetes: commonly uses an emptyDir, ephemeral storage or a mounted volume.

Its capacity is determined by the node or volume configuration, not by spark.executor.memory. If it fills, tasks usually fail with an I/O error such as “No space left on device.” Size it for concurrent shuffle files, spill runs and safety headroom.

Executor settings do not allocate a private disk

spark.executor.memory          → executor JVM heap
spark.executor.cores           → concurrent task capacity
spark.executor.memoryOverhead  → non-heap/container memory
spark.local.dir                → scratch-space location, not its capacity

The usable capacity comes from the worker machine’s local disks and attached volumes, minus space consumed by the operating system, platform services, logs, caches, spills, other shuffle generations and other applications. Disk is generally a worker-node resource rather than a private resource assigned to one executor. Executors or applications placed on the same worker may share it.

Databricks

On Databricks, the selected worker node type determines the base local SSD or NVMe storage. Additional attached cloud volumes and the platform’s autoscaling-local-storage option can increase that capacity. Databricks commonly runs one Spark executor on each worker, so most usable worker-local storage is effectively available to that executor, but it remains node-level storage.

To determine the actual capacity, check the worker node type in the Compute configuration, inspect that cloud instance type’s local-storage specification, check for additional or elastic disks, and inspect the mounted filesystems at runtime. A command such as df -h /local_disk0 shows the filesystem visible on the machine where it runs; a notebook shell command commonly describes the driver, so worker measurements should be executed across workers when worker-level confirmation is required.

YARN

YARN executors use the NodeManager paths supplied through LOCAL_DIRS, based on yarn.nodemanager.local-dirs. For executor processes, these cluster-manager paths override spark.local.dir.

yarn.nodemanager.local-dirs=/disk1/yarn/local,/disk2/yarn/local

The available shuffle space is therefore the usable capacity of the filesystems behind those paths. Requests such as --executor-memory 16g and --executor-cores 4 do not normally provide a corresponding private disk quota. Multiple YARN containers and applications can share the NodeManager disks. Check yarn-site.xml, run df -h for the configured paths on each worker, or obtain the usable per-NodeManager capacity from the cluster administrator.

Executor configuration → CPU and memory assigned to the process
Worker configuration   → local disk available for shuffle and spill

13. Is writing the planned shuffle output to local disk considered disk spill?

No. Shuffle write and spill are separate metrics and separate events.

14. Does every executor need 50 GB of disk and store 200 shuffle files?

No. Shuffle-data volume, local-disk capacity, logical bucket count and physical file count are four different concepts.

First correction: 50 GB is an estimated total shuffle volume, not disk capacity

If this job writes approximately 50 GB of shuffle data in total and two executors run a roughly equal share of the map tasks, each executor may store approximately 25 GB of map output:

Estimated total shuffle output: 50 GB
Executor A map-output share:    approximately 25 GB
Executor B map-output share:    approximately 25 GB

This is only an illustration. Partial aggregation and compression may make the shuffle much smaller; wide rows, joins, repartitioning or multiple concurrent stages may make local-disk usage larger.

The disk itself must provide more capacity than the executor’s expected share because it may also contain spill runs, multiple shuffle generations and safety headroom. Disk capacity is supplied by the node or mounted volume; it is not determined by the executor’s 16 GB heap.

Second correction: 200 logical buckets do not mean 200 physical files per map task

With normal sort-based shuffle, a map task typically produces:

  • One consolidated map-output data file containing its bucket segments back to back.
  • One index file containing the start and end offsets for those segments.

Therefore, a “shuffle segment file” is usually better described as a shuffle block: a byte range inside the map task’s consolidated data file, located through its index file. That data file is normally stored in Spark’s local scratch directories on the worker where the map task ran. Specialized remote-shuffle implementations are an exception to this normal local-disk model.

Map task M0 data file:
[Bucket 0 segment][Bucket 1 segment] ... [Bucket 199 segment]

Map task M0 index file:
[offset B0][offset B1] ... [offset B200 end]

Corrected two-executor example

Assume 50 GB of total input, approximately 400 map tasks, approximately 50 GB of total shuffle output, two equally used executors and 200 shuffle partitions:

How one reducer reads its bucket

If an average map-output data file is approximately 128 MB and contains 200 logical segments, the illustrative average segment size is:

128 MB ÷ 200 ≈ 0.64 MB per bucket segment

Reducer 57 reads the index for every map output and fetches only the Bucket-57 byte range:

≈400 map outputs × ≈0.64 MB
≈256 MB average total for reducer 57

This matches:
50 GB total shuffle ÷ 200 reducers ≈256 MB per reducer

Real segment sizes are not equal: some may be empty, key distribution may be uneven, and skew can make one bucket much larger than the average.

Why sort-based shuffle matters

Older shuffle approaches could create a physical file for every mapper-and-reducer combination, producing extremely large file counts. Sort-based shuffle’s consolidated data-plus-index layout avoids that per-bucket physical-file explosion.

15. Where does a UDF run: driver or executors?

A UDF normally executes inside stage tasks on every executor that processes relevant partitions. The driver plans the operation and distributes the function definition; it does not centrally evaluate every row.

Driver
  └─ builds plan and ships UDF code/closure with the stage

Executor A
  ├─ task for P0 → invokes UDF for P0 rows
  └─ task for P1 → invokes UDF for P1 rows

Executor B
  ├─ task for P2 → invokes UDF for P2 rows
  └─ task for P3 → invokes UDF for P3 rows

The UDF is not permanently assigned to one particular executor. Whichever executor receives a task containing that UDF must have the code and dependencies needed to execute it. Later task waves, retries and speculative attempts can execute the same UDF on different executors.

UDF typeWhere row evaluation occursImportant boundary
Scala/Java UDFInside the executor JVM running the taskOften limits Catalyst optimization compared with equivalent built-in SQL expressions
Standard Python UDFIn a Python worker process associated with the executorRows cross the executor JVM ↔ Python serialization boundary
Pandas/Arrow UDFIn an executor-side Python worker, processing Arrow batchesVectorization reduces per-row crossing overhead but still introduces a Python execution boundary

The physical plan determines when the UDF runs. If it appears before an Exchange, shuffle-map tasks evaluate it; if it appears after an Exchange, downstream shuffle-read tasks evaluate it. Look for operators such as BatchEvalPython, ArrowEvalPython or the relevant projection/filter in explain().

Practical rule: use built-in Spark SQL functions when an equivalent exists. They usually allow Catalyst optimization and JVM code generation without the Python worker boundary.

1

Characterize the workload before sizing anything

Record more than the 50 GB input size:

  • File format and compression: 50 GB of compressed Parquet can decode to considerably more data.
  • Wide transformations: groupBy, join, distinct, orderBy and repartition create Exchanges.
  • Join sizes: a small dimension may be broadcast; a large-to-large join normally shuffles both sides.
  • Key cardinality and skew: a few hot keys can dominate one reducer regardless of total file size.
  • Caching, Python UDFs and concurrent jobs: these add memory or CPU pressure.
  • The required completion time: executor count is mainly an SLA and concurrency decision.
2

Calculate input parallelism

For a splittable Parquet input and an illustrative 128 MB target:

50 GB × 1024 ÷ 128 MB ≈ 400 input partitions ≈ 400 Stage-0 scan tasks

This calculation determines task count, not executor count. Executors only control how many of those tasks run simultaneously.

3

Estimate the shuffle volume and choose shuffle partitions

Use the estimated post-combine shuffle bytes, not blindly the input size:

shuffle partitions ≈ estimated shuffle bytes ÷ target reducer-partition size

With a 128–256 MB target:

  • 50 GB shuffle → roughly 200–400 partitions.
  • 100 GB shuffle → roughly 400–800 partitions.
  • Partial aggregation may shrink a groupBy().count() shuffle substantially.
  • A large join or repartition may generate shuffle volume close to or greater than the input.

Start with a defensible estimate and enable Adaptive Query Execution so Spark can coalesce small partitions and handle skewed joins.

spark.sql.adaptive.enabled = true spark.sql.adaptive.coalescePartitions.enabled = true spark.sql.adaptive.skewJoin.enabled = true
4

Choose cores per executor

A practical starting point is usually 4–5 cores per executor.

  • Four cores allow four concurrent tasks per executor.
  • Very large executors create more concurrent memory consumers, longer garbage-collection pauses and greater loss when one executor fails.
  • One-core executors isolate tasks but create excessive executor and scheduling overhead.

For this workload, begin with four cores per executor unless measurements show a CPU, I/O or memory reason to change it.

5

Estimate executor heap and memory overhead

Memory is shared dynamically; cores do not receive fixed slices. Size for the simultaneous working state of all active tasks:

executor heap ≈ (cores × peak execution memory per active task) + cached data + safety margin

For four cores running 128–256 MB partitions with wide aggregations or joins, a reasonable initial range is:

  • 16–24 GB executor heap.
  • 4–6 GB memory overhead for direct buffers, native memory, container overhead and Python workers where applicable.
  • Use the higher end for Python UDFs, large broadcast variables, heavy serialization or high-cardinality aggregation state.

The correct value comes from peak execution memory, spill and garbage-collection metrics—not from multiplying the 50 GB file by an arbitrary factor.

6

Choose the number of executors from desired task waves

total task slots = executors × cores per executor task waves ≈ stage tasks ÷ total task slots

With 400 input tasks and four-core executors:

  • 2 executors → 8 slots → approximately 50 Stage-0 waves.
  • 4 executors → 16 slots → approximately 25 waves.
  • 6 executors → 24 slots → approximately 17 waves.
  • 8 executors → 32 slots → approximately 13 waves.

More executors reduce the number of waves until storage throughput, network capacity, scheduler overhead or downstream systems become the bottleneck.

7

Plan local disk and shuffle capacity

Wide transformations need local storage for map-output files and spills. Estimate peak shuffle and spill volume, distribute it across executors, and leave substantial safety headroom.

  • Fast local SSD is strongly preferred for shuffle-heavy workloads.
  • Disk capacity must cover map outputs, reducer spills and concurrent stages or jobs.
  • Disk throughput determines performance; disk capacity determines whether the job can finish.
  • “No space left on device” is a disk failure, not an executor-heap OOM.
8

Select join and skew strategies before adding hardware

  • Broadcast a genuinely small join side when it safely fits on every executor.
  • For large-to-large joins, expect an Exchange and size shuffle partitions appropriately.
  • Use AQE skew-join handling for uneven partitions.
  • Salt only measured hot keys; calculate salt count from hot-key bytes and the desired partition size, then benchmark it.
  • Avoid unnecessary repartition(); use it only when the downstream distribution benefit justifies another full shuffle.
9

Run a representative test and read the Spark UI

Validate the starting configuration with production-like data. Inspect:

  • Median, 95th-percentile and maximum task duration and input size.
  • Shuffle read/write bytes, remote fetch wait and network throughput.
  • Memory spill, disk spill and peak execution memory.
  • Garbage-collection time, executor loss and scheduler delay.
  • Whether all task slots remain busy or the job is limited by one skewed reducer.
10

Change one dimension at a time

Use evidence rather than adding memory and cores together. Re-run the same representative workload after each change.

repartition(1) versus coalesce(1)

Both operations return a DataFrame with one output partition, but they reach that result through very different dependency graphs. The example below starts with four parent partitions across two executors with two cores each.

The physical plans

df.repartition(1)

Exchange SinglePartition
+- Existing parent plan

The Exchange creates a wide dependency and normally a new stage boundary. Every upstream partition can contribute rows to the one new partition.

df.coalesce(1)

Coalesce 1
+- Existing parent plan

Coalesce creates a narrow dependency. One child partition directly references all four parent partitions. Coalesce itself does not insert an Exchange.

What happens inside the executors?

repartition(1)

  1. M0 and M1 run on Executor A; M2 and M3 run on Executor B.
  2. All four map tasks target the only global shuffle bucket: Bucket 0.
  3. Each mapper writes one Bucket-0 segment into its local shuffle data file.
  4. The single reducer runs on one executor and fetches all four segments.
  5. Same-executor segments are local reads; other-executor segments cross the network.
  6. The reducer produces one final partition and one output file if the DataFrame is written.

coalesce(1)

  1. Spark creates one child partition C0 that depends on P0, P1, P2 and P3.
  2. One task runs C0 on one available core.
  3. The task reads or computes P0, then P1, then P2, then P3.
  4. The second executor and remaining cores can be idle during this downstream operation.
  5. No map-output shuffle files or reducer fetches are created by coalesce.
  6. C0 produces one final partition and one output file if written.
Important lazy-evaluation nuance: partitions are logical lineage, not necessarily fully materialized data already sitting in executor memory. Without caching, the coalesced task can compute the parent partitions as it iterates them. If the parent DataFrame was cached across executors, the coalesced task may read local or remote cached blocks through the BlockManager, but that is still not a shuffle Exchange.

How the key buckets line up

For Sort-Merge Join and Shuffle Hash Join, compatible partitioning ensures that every row for the same key reaches the same join task:

Bucket 0 · key AOrders: A rowsCustomers: A row
Bucket 1 · key BOrders: B rowsCustomers: B row
Bucket 2 · key COrders: C rowsCustomers: C row
Bucket 3 · key DOrders: D rowsCustomers: D row

Bucket 2’s join task fetches only Bucket-2 segments from the map outputs of both tables. It never needs rows belonging to Buckets 0, 1 or 3.

Strategy-selection thought process

  1. Check table statistics and the actual optimized plan using explain().
  2. If one side is safely small, Broadcast Hash Join usually avoids the expensive large-side shuffle.
  3. If both sides are large, Sort-Merge Join is the common robust strategy because sorting can spill to disk.
  4. Consider Shuffle Hash Join when the build-side partition is much smaller than the probe-side partition and safely fits in execution memory.
  5. Check key skew. A hot key makes one join bucket much larger even when the average bucket size looks safe.
  6. Allow AQE to use runtime statistics to change join strategies or split skewed partitions when appropriate.

Is DataFrameWriter.partitionBy(...) a wide transformation?

No—not by itself in the standard Spark file-writer path.

df.write.partitionBy("country").parquet(path)

Existing P0–P3
      ↓
4 writer tasks keep their existing inputs
      ↓
Each task locally routes rows into country directories

The writer may add task-local sorting, buffering or spilling so rows for the same destination are processed together, but this does not inherently create a network shuffle, an Exchange, shuffle-map tasks or a downstream shuffle-read stage.

repartition(10, "country") → Exchange/shuffle → wide transformation
partitionBy("country")     → destination directory layout

After repartition(10, "country"), the ten downstream Spark partitions normally become ten final write-task inputs. partitionBy then determines which destination directories those tasks write into.

How to verify: look for Exchange in explain(). In the Spark UI, a true shuffle has a shuffle-write stage followed by downstream shuffle-read tasks. A table format, data source or platform optimization can insert redistribution even though partitionBy itself does not mandate it.

Where does writer routing happen: driver or executor?

Writer routing happens inside each write task on the executor running that task. The driver does not receive all rows and route them itself.

ComponentResponsibility
DriverBuilds the physical plan, creates the write stage, schedules tasks, tracks completion and coordinates the final job or table commit.
Executor write taskReads one Spark partition, evaluates the partitionBy columns for each row, selects the destination directory and writes that task’s output files.
Executor local diskHolds temporary sort/spill data when the task cannot organize everything in memory. It is not normally the final table location.
Destination storageReceives the output files through the configured file system and commit protocol—for example HDFS, cloud object storage or a mounted filesystem.
 
Driver
  ├─ schedules writer task P0 → Executor A
  ├─ schedules writer task P1 → Executor A
  ├─ schedules writer task P2 → Executor B
  └─ schedules writer task P3 → Executor B

Executor A · task P0
  ├─ IN rows → country=IN/part-P0...
  └─ US rows → country=US/part-P0...

Executor B · task P2
  ├─ US rows → country=US/part-P2...
  └─ UK rows → country=UK/part-P2...

Therefore, routing can occur concurrently on every executor that currently has a write task. It is not permanently assigned to one particular executor: the Spark scheduler can place later task waves—and failed-task retries—on any suitable executor with an available slot.

100 Spark partitions + 8 available task slots
→ 100 write tasks

If an explicit repartition is present, both phases still execute on executors: shuffle-map tasks perform the first hash routing and write shuffle blocks, then downstream shuffle-read/write tasks fetch their blocks and perform the final destination-directory routing.

What memory, disk and serialization mean

TermPhysical meaningMain trade-off
MemoryThe executor’s storage-memory region, normally inside its JVM heap—not driver memory. It shares Spark’s unified memory area with execution.Fast reuse, but blocks can be evicted under pressure.
DiskExecutor-local scratch storage managed by the BlockManager, under Spark/cluster-manager local directories. It is not the durable source table, HDFS or cloud output location.Slower than memory and normally lost with the executor/node, but avoids recomputing an available local block.
DeserializedJava/Scala objects remain expanded in executor memory and can be consumed directly.Fastest CPU access, usually the largest memory footprint and more garbage-collection pressure.
SerializedEach partition is stored as a compact byte representation and must be deserialized when read.Usually smaller memory footprint, with extra CPU cost on every reuse.
API nuance: MEMORY_ONLY_SER and MEMORY_AND_DISK_SER are most meaningful for Java/Scala RDDs. Python objects are serialized with Pickle for storage regardless of choosing a “SER” name. Spark SQL DataFrames use Spark’s optimized cached representation—commonly columnar and compressed—rather than simply keeping ordinary JVM row objects.

Distribution, locality and fault recovery

  • The scheduler decides which executor computes each partition. The resulting cache placement follows those task assignments; it is not necessarily round robin.
  • Later actions prefer an executor already holding the required block, reducing network transfer and recomputation.
  • Cached disk means local worker disk. If that executor or worker disappears, those blocks normally disappear with it and Spark recomputes them from lineage.
  • Levels ending in _2 replicate every block to a second executor, trading extra storage and network traffic for faster recovery.
  • MEMORY_ONLY does not automatically spill uncached partitions to disk. A partition that cannot stay cached must be recomputed when needed again.

Exact distinct versus HyperLogLog++

  • Exact distinct must preserve enough information to prove whether every value has appeared, so shuffle/state grows with cardinality and may spill.
  • HyperLogLog++ hashes values into a fixed set of registers. Each partition builds a compact sketch, and sketches are merged register by register.
  • relativeSD controls the accuracy/space trade-off: a smaller allowed error requires a larger sketch.
  • On this tiny dataset, the illustration reports approximately six distinct users. Approximate algorithms are most valuable when the real cardinality is extremely large.
